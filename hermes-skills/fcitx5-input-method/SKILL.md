# Fcitx5 input method: install, migrate, theme, patch

Class: installing/migrating to fcitx5, wiring addons (cloud pinyin, local-LLM IMEs like Cassotis), theming the candidate window to match pywal/dwm, and source-patching addons.

## When to Use

- Migrating fcitx4 → fcitx5, adding input methods (pinyin/mozc/hangul/unikey/Cassotis), enabling cloud pinyin, theming the candidate window, or patching fcitx5 addon behavior.

## Always-on rules

- **NEVER run `pkill fcitx` / `pkill fcitx5` from the Hermes agent terminal — CONFIRMED by user: it freezes the terminal running Hermes.** fcitx holds the X keyboard filter mid-operation and killing it (or matching the agent's own wrapping shell) wedges input. The ONLY sanctioned stop is `fcitx5-remote -e` (graceful DBus exit), then `sleep 2`, then relaunch `fcitx5 -d` in the same command. If `fcitx5-remote -e` doesn't take, STOP and tell the user to kill it from their own session — do not escalate to pkill yourself. This applies to every workflow below that says `pkill -x fcitx5`: substitute `fcitx5-remote -e`.
- **fcitx5 rewrites its own conf files on clean exit** (profile, pinyin.conf, classicui.conf get regenerated with defaults for keys it considers unset). ALWAYS stop fcitx5 first (`fcitx5-remote -e; sleep 2; pkill -x fcitx5`), THEN edit conf, THEN start. Editing while running = your edits vanish at next restart.
- **classicui.conf keys must be top-level — no `[General]` section header.** A section header makes every key silently ignored and the candidate window stays white/default. Correct: `Theme=wal` as the first line, no bracket header.
- **Addon version deps are silent.** An addon whose `[Addon/Dependencies] core:X.Y.Z` exceeds the installed fcitx5 core is skipped with no user-visible error — the IM just never appears. Diagnose with `fcitx5 -d --verbose 'default=4'` and grep the log for `Loaded addon <name>`. Fix by upgrading core (e.g. PPA `ppa:ayanamist/fcitx5` provides newer fcitx5 on Ubuntu noble) — do not reinstall the addon.
- **Frontend immodules are separate packages.** Engine installed but keystrokes pass straight through the app = missing frontend modules. Package names are distro-specific: Debian/Ubuntu `fcitx5-frontend-gtk3/gtk4/qt5`; Void `fcitx5-gtk+2 fcitx5-gtk+3 fcitx5-gtk4 fcitx5-qt5 fcitx5-qt6` (xbps-query -Rs fcitx5 to list). Install the full set for GTK2/3/4 + Qt5/6.
- **Env vars for fcitx5:** `GTK_IM_MODULE=fcitx5`, `QT_IM_MODULE=fcitx5`, but `XMODIFIERS=@im=fcitx` stays (XIM name unchanged). Already-running apps keep old env — they need relogin or a fresh launch with the new vars.
- **`fcitx5 -v` is `--version`, not verbose.** Verbose logging is `--verbose 'default=4'` (levels 0-5, categories like `key_trace`). `-D` runs foreground (blocks); `-d` daemonizes.

## Workflow: verify an IME end-to-end

1. Start fcitx5, confirm addon loaded: `fcitx5 -d --verbose 'default=4' >log 2>&1; grep 'Loaded addon <name>' log`.
2. Add to profile (`~/.config/fcitx5/profile`, `[Groups/0/Items/N]` blocks with `Name=<im>`), done while fcitx5 stopped.
3. Test in a FRESH window launched with the new env: `DISPLAY=:0 GTK_IM_MODULE=fcitx5 QT_IM_MODULE=fcitx5 XMODIFIERS=@im=fcitx st -e bash -c 'sleep 120'` (background). Find its window by PID: `wmctrl -lp | awk '$3==<pid>'` — never trust `xdotool search --class st | tail -1`; the agent's own terminal matches the class and you will type into yourself.
4. Activate explicitly before typing: `fcitx5-remote -s <im>` then `fcitx5-remote -o` (activate). State check: `fcitx5-remote` returns 2 = active. Without `-o` the IM is selected but inactive and raw pinyin leaks into the app.
5. `xdotool type --delay 80 '<pinyin>'`, wait for async candidates (cloud/LLM results arrive 1-3s late), `import -window root shot.png`, vision_analyze.

## Workflow: cloud pinyin (fcitx5)

Enable, ☁-label source patch, Void build recipe, and verification (dedup means frequent words never show ☁; test with absurd long phrases) — see `references/cloud-pinyin-patch.md`. Always-on summary: patch `fill()` in `cloudpinyin_public.h`, rebuild BOTH pinyin+cloudpinyin, INSTALL both .so (build ≠ install), verify ☁ bytes with `LC_ALL=C grep`, restart with `fcitx5-remote -e` + `fcitx5 -d`.

## Workflow: static extra dictionaries (zhwiki / web-slang / sogou) for fcitx5-pinyin

- Sogou full dict without AUR: `github.com/blackteahamburger/fcitx5-pinyin-sougou-dict` releases (monthly, e.g. tag 20260920) ship prebuilt fcitx5-native `sougou.dict` (~136MB) — just drop into `~/.local/share/fcitx5/pinyin/dictionaries/`. (Original AUR source repo maoyaotang12/sougouscel is 404'd.) Void has `scel2org5` + `libime_pinyindict` if ever converting raw .scel by hand.
- Verify sogou dict loaded: type `neijuan` → 内卷 in candidates (screenshot).

- Void has no `fcitx5-pinyin-zhwiki` package. Install manually from `github.com/felixonmars/fcitx5-pinyin-zhwiki/releases` (latest tag, newest dated files): download the fcitx5-native `zhwiki-<date>.dict` (~32MB) and `web-slang-<date>.dict` (NOT the `.dict.yaml` Rime variants) into `~/.local/share/fcitx5/pinyin/dictionaries/` (create dir). Stop fcitx5 first, drop files, restart — pinyin addon picks them up on next start, no config edit needed.
- Verify the dict is actually consulted (not just "pinyin works"): type a wiki-only proper noun, e.g. `habusibao` → 哈布斯堡 must appear as a candidate; base libime dict doesn't have it. Screenshot the candidate window.
- Cloud pinyin verification has no visual marker in fcitx5: type a long sentence and check `ss -tnp | grep fcitx5` for established :443 connections to Google IPs during input.
- 搜狗 dict (搜狗细胞词库): installed on this box as `~/.local/share/fcitx5/pinyin/dictionaries/sougou.dict` (~136MB, converted via libime_tool from .scel; source per AUR fcitx5-pinyin-sougou-dict, custom license). Picked up automatically by pinyin addon on restart, no config edit. To update: re-convert from .scel with `libime_pinyin_dict_gen` (or the AUR build script) and swap the file while fcitx5 is stopped (`fcitx5-remote -e`).

## Workflow: pywal-matched candidate theme

- **User's standing contrast requirement: candidate window background must be near-black/deep gray — never light.** Light-blue bg + white text is invisible to the user. Current approved palette in the generator: BG `#101418`, normal/highlight text `#ffffff`, selection bg `#2f6fb0`, border `#3a4750`. Never regenerate with a light/pastel bg without asking.
- Generate `~/.local/share/fcitx5/themes/wal/theme.conf` from `~/.cache/wal/colors` (bg=color0, text=color7, highlight bg=color8, border=color4), mirroring the stock `default-dark` theme's section structure (`[InputPanel]`, `[InputPanel/Background]`, `[InputPanel/Highlight]`, `[Menu/...]`). Invented section names (`CurrentCandidate`, `CandidateHighlight`) are silently ignored — copy the stock dark theme's real keys: `HighlightBackgroundColor`, `HighlightCandidateColor`.
- Keep the generator at `~/.local/bin/fcitx5-waltheme` and hook it into wal palette changes via `~/.config/wal/on_change.d/50-fcitx5.sh` so wallpaper swaps re-sync the IME.
- Cycle-IM hotkey pattern: a small `fcitx5-imnext` script (reads `fcitx5-remote -n`, walks a fixed IM list, `fcitx5-remote -o` + `-s <next>`) bound via xbindkeys on key RELEASE (`"fcitx5-imnext"` / `Release + Mod4 + control + i` in `.xbindkeysrc`) — Release-triggered so one physical keypress = one cycle step regardless of hold duration (see auto-repeat pitfall). Scripts live in `~/.local/bin/`, NOT auto-tracked — see dotfiles sync below. When adding an IM to the cycle, edit BOTH the fcitx5 profile AND the hardcoded `LIST=` in the script — the hotkey is blind to profile-only changes.

## Workflow: Rime with rime-ice (雾凇拼音)

1. Install engine: `apt install fcitx5-rime` (any recent build; librime plugins charcode/octagram come along). No rime data dir is created until first run.
2. Populate user data dir by git clone (NOT plum — a plain clone keeps updates trivial): `mkdir -p ~/.local/share/fcitx5/rime && git clone --depth=1 https://github.com/iDvel/rime-ice ~/.local/share/fcitx5/rime`. The clone ships its own AGENTS.md with repo conventions — follow it if editing dicts (edit `cn_dicts/`/`en_dicts/`, never the generated `*.dict.yaml` master).
3. Add `rime` to the fcitx5 profile (stopped first) and to the `fcitx5-imnext` cycle list — the cycle list is a hardcoded `LIST="..."` in the script, so a new IM is invisible to the hotkey until the script is edited too.
4. Start fcitx5 and trigger deployment: `fcitx5-remote -s rime`, then wait ~15-30 s — librime compiles schemas asynchronously on first activation. Verify by artifacts, not by the remote exit code: `ls ~/.local/share/fcitx5/rime/build/*.bin` (a `rime_ice.table.bin` in the MB range + per-schema `.prism.bin` = success).
5. If the auto-deploy stalls partway — build dir has only stock schemas (luna_pinyin etc.) and no `rime_ice.*.bin`, and re-selecting rime never completes — the in-process deployer died silently. Fix by running the standalone deployer once: `rime_deployer --build ~/.local/share/fcitx5/rime` (ships with librime/fcitx5-rime), then restart fcitx5. Check `installation.yaml` in the data dir: its presence means the deployer ran at least once; a build dir missing the user's schema means it aborted.
6. Update later: `git pull` in the data dir, `pkill -x fcitx5; fcitx5 -d`, re-select rime — it recompiles changed tables automatically. Custom user phrases survive in `~/.local/share/fcitx5/rime/sync/` only if the user syncs; local edits to tracked files will conflict on pull — keep customizations in `custom_phrase.txt` / `installation.yaml`-adjacent untracked files where possible.
7. Switch default schema (e.g. 全拼→双拼): write `~/.local/share/fcitx5/rime/default.custom.yaml` containing `patch: {schema_list: [...]}` — the rime-sanctioned override that survives `git pull` of the data dir; do NOT edit the tracked `default.yaml`. Restart fcitx5 or let the user pick via F4 in-session.
8. **A schema with unmet `dependencies:` compiles to NOTHING silently.** wanxiang (万象) declares `wanxiang_mixedcode/_reverse/_english/_abbrev/_phrase` dicts; if those `*.dict.yaml` files aren't in the data dir, `rime_deployer` still exits 0 with zero output and no `wanxiang.*.bin` is produced — selecting the schema then shows no candidates at all, looking like an ascii-mode bug. Diagnose: grep the schema's `dependencies:` block and check each name has a matching `.dict.yaml` in the data dir; verify success ONLY by `ls build/<schema>.table.bin` after deploy, never by exit code. Fix by installing the missing dict files or removing the schema from `schema_list`.
9. Official 朙月拼音 (luna_pinyin, 中州韵) installs cleanly by copying `luna_pinyin*.schema.yaml` + `luna_pinyin.dict.yaml` + `pinyin.yaml` from `github.com/rime/rime-luna-pinyin`, plus `stroke.schema.yaml`/`stroke.dict.yaml` from `rime/rime-stroke` (its reverse-lookup dep) and `symbols.yaml` from `/usr/share/rime-data/` — rime-ice renames its symbols to `symbols_v.yaml` so the stock name is missing. luna_pinyin defaults to TRADITIONAL output; user toggles simplified with Ctrl+Shift+4 (built into the schema).

## Verifying from a headless/agent session (no focused input window)

- `fcitx5-remote -n` returns EMPTY when no client app has focus — this is normal, not a failure, and cannot be used to prove IM switching from the agent terminal. Reliable headless checks instead: `fcitx5-remote -a` (prints the DBus address = daemon alive), `fcitx5-remote -m <im>` (resolves IM → addon name = IM registered), and the daemon log line `Loaded addon <name>`. Ask the user to test switching in a real window; don't claim switching is broken based on empty `-n` output.
- **Void/runit autologin + auto-startx pattern**: edit `/etc/sv/agetty-tty1/conf` adding `GETTY_ARGS="--noclear --login-options '-f <user>'"` (pam_securetty only gates root, plain users fine), then in `~/.bash_profile` add guarded `exec startx`: `[ -z "$SSH_CLIENT" ] && [ -z "$SSH_TTY" ] && [ "$(tty)" = /dev/tty1 ] && ! pgrep -x Xorg`. Use bare `startx` — it auto-adds `vt$XDG_VTNR` (elogind sets it); explicit `:0 vt1` args are redundant. Apply with `sudo sv restart agetty-tty1` (safe mid-X-session; the Xorg guard prevents double-start).
- **Session bus must be established BEFORE fcitx5 starts in .xinitrc** (Void has no systemd user bus): export XDG_RUNTIME_DIR + dbus-daemon --session on /run/user/1000/bus + DBUS_SESSION_BUS_ADDRESS at the TOP of .xinitrc, before the `fcitx5 -d` line. A busless fcitx5 still grabs the X keyboard filter → hotkeys swallowed, browsers see nothing. Self-heal snippet in .xinitrc kills any fcitx5 whose /proc/<pid>/environ lacks DBUS_SESSION_BUS_ADDRESS before starting a proper one.
- **End-to-end IME verification in browsers (agent-driven)**: `xdotool windowactivate --sync <win>` then `key ctrl+l` (focus URL bar), `key ctrl+space`, `type --delay 120 'nihao'`, `sleep 2`, `maim -u shot.png`, vision_analyze for preedit+candidate popup. Caveats: `xdotool search --class firefox` returns multiple windows — the content window vs chrome differ; ctrl+l on the wrong window leaks keystrokes into the agent's own terminal (never trust first/tail blindly, verify focus in the screenshot). Toggle state before typing matters: state 2 = pinyin active; if you toggle from 2 you land on 1 (English) and raw pinyin leaks — check `fcitx5-remote` right before typing. `maim` is the screenshot tool on this box (no scrot/import).
- **gnome-keyring missing = silent secrets failure**: .xinitrc's `eval "$(gnome-keyring-daemon --start ...)"` fails silently when the package isn't installed (Void: `xbps-install gnome-keyring`, pulls gcr). Verify with `dbus-send --session --print-reply --dest=org.freedesktop.secrets /org/freedesktop/secrets org.freedesktop.DBus.Introspectable.Introspect`. Run foreground variant `gnome-keyring-daemon --foreground --components=secrets` when starting from agent background (plain --start daemonizes and may die with the calling shell).
- Multiple fcitx5 instances fight over the DBus name: a second start logs `Failed to create addon: dbus Unable to request dbus name` and runs crippled. Always `pkill -x fcitx5; sleep 1` before relaunching, and confirm exactly one PID with `pgrep -x fcitx5`.
- **Stale instance WITHOUT DBUS_SESSION_BUS_ADDRESS silently eats global hotkeys.** A fcitx5 launched outside the session bus (no DBUS_SESSION_BUS_ADDRESS in /proc/<pid>/environ) still installs the X keyboard filter, so it swallows Ctrl+Space and toggles its own crippled state while the browser-facing daemon (org.fcitx.Fcitx5 owner) never sees the key. Symptom: hotkey dead in Firefox/Brave but config intact; `fcitx5-remote` may return 'Failed to get reply'. Diagnose: `ps -o pid,lstart -p $(pgrep -x fcitx5)` + check each PID's environ for DBUS_SESSION_BUS_ADDRESS; check name owner via dbus-send GetConnectionUnixProcessID string:org.fcitx.Fcitx5. Fix: kill the stale PID, `pkill -x fcitx5; sleep 1; fcitx5 -d`, verify toggle with a REAL held combo (`xdotool keydown ctrl; keydown space; sleep 0.5; keyup ...` — a bare `keydown ctrl` alone tests nothing) and `fcitx5-remote` state 0↔2.

## Syncing local fcitx5 bits to the dotfiles repo

Live fcitx5 files often exist only in `~/.local/bin` / `~/.config` while the dotfiles repo clone tracks canonical copies (current repo: `~/mac6void` → i0day/mac6void; see the `dotfiles-sync-mac6void` skill for the authoritative layout — `~/.local/bin/*` → `local/bin/*`). To sync:
1. `git remote -v` first — remote names drift between clones; never assume the push target's remote name from memory.
2. `cp` live files in, `git add -A`, commit, push with `GIT_ASKPASS=~/askpass.sh` (token at `~/gittoken`; never in `.git/config`).
3. Diff live vs repo first to find live-only changes; live config is the source of truth, the repo drifts silently.
4. NEVER sync the rime user dir wholesale — `wanxiang-lts-zh-hans.gram` (~400MB) and `build/` are binary/regenerable. Sync only `default.custom.yaml` (schema_list patch) plus a docs file recording the schema set and install recipe.

## Closed-source Chinese IMEs on Linux (讯飞/iflyime etc.)

- 讯飞输入法 Linux 版 (iflyime 2.0.51) is a **fcitx4-only** addon — its `fcitx-iflyime.so` links `libfcitx-config.so.4`/`libfcitx-utils.so.0` and it declares fcitx4 deps (fcitx-module-kimpanel, libgrpc++1, libprotobuf17). It cannot coexist with a fcitx5 stack; installing it means replacing the whole framework and losing fcitx5 addons/themes. Void has no package. Check `ldd <im>.so | grep fcitx` inside any candidate deb BEFORE proposing the install. If the user only wants 讯飞's voice-input feature, use a standalone dictation tool instead — see `references/voice-input-linux.md` (decision table + the user's verified local whisper.cpp `voice-type` recipe on Super+Ctrl+V).
- iFlytek's CDN 403s on direct deb downloads; needs browser UA + referer `https://srf.xunfei.cn/` (the AUR iflyime PKGBUILD URL works with those headers).

## Pitfalls

- Cassotis (local-LLM pinyin, .deb with ONNX models) requires fcitx5 core ≥ 5.1.19; Ubuntu noble ships 5.1.7 — the addon silently never loads until core is upgraded from the ayanamist PPA.
- Duplicate candidates get deduped by fcitx5, so a labeled cloud candidate won't appear on every input — absence of the label is not a failure signal; check `ss` connections instead.
- Build deps for fcitx5-chinese-addons on noble: cmake, extra-cmake-modules, fcitx5-modules-dev, libimecore/libimepinyin/libimetable-dev, libopencc-dev, nlohmann-json3-dev, libboost-dev, libcurl4-openssl-dev; skip Qt with `-DENABLE_GUI=OFF -DENABLE_BROWSER=OFF -DENABLE_TEST=OFF`.
- Keep patched source outside the scratch dir (scratch is pruned after 24h idle) — move to `~/src/` and export the diff as a .patch into the dotfiles repo so the rebuild survives machine loss.
- `fcitx5 --verbose ... > ~/.something.log &` fails twice over in the agent terminal: `&` backgrounding is blocked in foreground calls, and a redirect into a home dotfile trips the security scan. Use `fcitx5 -d` (daemonizes, no `&` needed) or write the log under `~/.hermes/cache/scratch/` with terminal(background=true). Grepping the daemon log for `Loaded addon rime` is the reliable check that the addon registered — `fcitx5-remote -s rime` returning 0 alone does NOT prove the engine deployed.
- xbindkeys silently loses its key grabs after X-session churn (restarting fcitx5, WM restart, lock/unlock cycles) — the daemon still runs but the hotkey does nothing, with no error. Fix without logout: `pkill -x xbindkeys; sleep 1; xbindkeys`. Diagnose by running the bound script manually (works) vs `xdotool key --clearmodifiers <combo>` + state check (`fcitx5-remote -n`) — script-works/hotkey-dead = lost grab, not a script bug.
- Pick hotkeys not claimed by focused apps: the app sees the key first, so xbindkeys never fires. Ctrl+Shift+I is Firefox devtools — never bind IM cycling there. Also check the WM's own bindings before choosing (dwm here uses Super+i / Super+Shift+i for layouts; Super+Ctrl+i is free). In `.xbindkeysrc` write the modifier as `Mod4` rather than `super` for reliable parsing.
- xbindkeys press-bindings fire on EVERY X auto-repeat event: holding the hotkey even briefly fires the script many times, and cycling N input methods an integer number of repeats lands back on the original IM — it looks like the hotkey 'does nothing' or 'switches wrong', and it's most visible in apps like Firefox where the user holds keys longer. Bind cycling hotkeys with the `Release` modifier (`Release + Mod4 + control + i`) so they fire exactly once per physical press. Diagnose with `xbindkeys -n -v -f ~/.xbindkeysrc >log` (background): the log shows each repeat as a separate `Key press !` + fork+exec.
- **`xdotool key --window <id>` delivers special keys (F4, Shift, Escape) to st/xterm as raw escape-sequence garbage** (`^[[0S` etc. lands in the input line) instead of real key events. For special keys: `xdotool windowfocus --sync <win>; windowactivate --sync <win>` then GLOBAL `xdotool key <keysym>` / `type` — no `--window`. Plain `type` with `--window` is fine, modifiers/function keys are not.
- Rime sits in ascii_mode by default after activation; raw pinyin leaking into the app means ascii_mode is on, not that the schema is broken. Single Shift press toggles 中/英; F4 opens the schema switcher menu (screenshot it to enumerate deployed schemas).
- xdotool `key`/`keydown`+immediate `keyup` is an instant press+release and CANNOT verify a `Release`-bound hotkey (it may appear dead). Simulate a real hold: `xdotool keydown super; keydown ctrl; keydown i; sleep 0.6; keyup i; keyup ctrl; keyup super`, then check `fcitx5-remote -n`.
- When killing a bar/daemon by pattern, `pgrep -f 'sbar'` matches the agent's OWN shell command line (the pattern string appears in the wrapping bash -c), so it looks like the process 'respawns' with a new PID each kill. Verify via the daemon's own PID file (`kill $(cat ~/.cache/pidofbar)`) or `pgrep -x <name>`, and restart daemons with terminal(background=true) — nohup/disown wrappers are blocked in foreground terminal calls. Same trap with `pkill -f <AppImage>`: it SIGTERMs the agent's own wrapping shell mid-command (exit -15) before the cleanup after it runs — find the real PID with `pgrep -af <name> | grep -v <agent wrapper markers>`, `kill <pid>` explicitly, then clean files in a separate call.
- **Never leave the terminal session's cwd inside a directory you delete** — every later `terminal()` call dies with `cd: No such file or directory` (exit 126) even when passing `workdir`, until something resets cwd. Fix: `cd /home/james` as its own command first, or do the deletion via `execute_code` (subprocess with explicit cwd) which is immune.
